[ 00 ] البداية

شنو هو الـ API أصلاً؟

تخيل نفسك رايح لمطعم. أنت "الزبون" ما تدخل للمطبخ وتطبخ اكلتك بنفسك، ولا تحچي مباشرة مع الشيف. بدل هذا تحچي مع النادل: تطلب منه الأكلة اللي تريدها من قائمة الطعام، هو ياخذ طلبك للمطبخ، والمطبخ يجهزها ويرجعها لك عن طريقه.

الـ API — اختصار Application Programming Interface، يعني "واجهة برمجة التطبيقات" — يشتغل بنفس الفكرة تماماً. هو "النادل" اللي يوصل الطلب بين برنامجين: برنامج يريد شي (يسمى Client / العميل)، وبرنامج ثاني عنده هذا الشي أو يقدر يسويه (يسمى Server / السيرفر). الـ API يحدد بالضبط: شنو الطلبات المسموحة (زي المنيو)، شلون تصيغ الطلب، وشنو شكل الجواب اللي راح يرجعلك.

💡
بكلمات أدق: الـ API هو مجموعة قواعد واتفاقيات — عقد — يحدد شلون برنامج (A) يطلب شي من برنامج (B) بدون ما يحتاج (A) يعرف شلون (B) مبرمج من الداخل. كل واحد منهم "صندوق أسود" بالنسبة للثاني، والـ API هو الباب الرسمي الوحيد المسموح تدخل منه.

مثال من الواقع

لما تفتح تطبيق الطقس بموبايلك، التطبيق نفسه ما عنده محطات رصد جوي! هو بس يرسل طلب (Request) لـ API تابع لجهة متخصصة بالطقس، هذا الـ API يرجّعله البيانات (درجة الحرارة، الرطوبة، توقعات الأيام الجاية) بصيغة منظمة، والتطبيق ياخذ هذي البيانات ويعرضها لك بشكل جميل. نفس المبدأ ينطبق على خرائط جوجل، بوابات الدفع الإلكتروني، وتسجيل الدخول بحساب Google أو Apple داخل تطبيقات ثانية.

ليش نحتاج الـ API؟

  • فصل الأجزاء عن بعض: فريق الواجهة الأمامية يقدر يشتغل ويطوّر التصميم بشكل مستقل، بشرط بس يتفق مع فريق الباك-اند على شكل الـ API من البداية.
  • إعادة الاستخدام: نفس الـ API الواحد تقدر تستخدمه تطبيقات مختلفة — موقع، تطبيق آيفون، تطبيق أندرويد — بدون ما تكرر نفس المنطق البرمجي بكل واحد.
  • الربط بين الأنظمة: تقدر تربط مشروعك بأنظمة عالمية جاهزة (خرائط، دفع، تواصل اجتماعي) بدون ما تبنيها من الصفر.
  • الأمان والخصوصية: الـ API يعرض بس الأشياء اللي تريد تعرضها، ويخفي كل التفاصيل الداخلية الحساسة زي قاعدة البيانات وبنية السيرفرات.
📌
وين راح نركز؟ فيه أنواع APIs كثيرة — حتى داخل نفس البرنامج الواحد توجد APIs بين المكتبات البرمجية المختلفة. هذي الدورة راح تركز حصراً على Web APIs: النوع اللي يشتغل عبر الإنترنت باستخدام بروتوكول HTTP، وهو الأكثر انتشاراً اليوم بعالم تطوير المواقع والتطبيقات، وهو اللي راح تصادفه ٩٩٪ من الأوقات كمطوّر مبتدئ.

[ 01 ] الأساسيات

كيف يشتغل هذا كله: Client-Server وHTTP

قبل ما نغوص بالتفاصيل، لازم نفهم شكل العلاقة الأساسية اللي يشتغل عليها أي Web API: نموذج العميل - السيرفر (Client-Server).

العميل يرسل طلب (Request)، والسيرفر يرد بجواب (Response) — هذي الدورة الكاملة تصير مرات بأجزاء من الثانية

العميل (Client) هو أي برنامج يبدأ الطلب: متصفحك، تطبيق الموبايل، أو حتى برنامج آخر بالكامل. السيرفر (Server) هو الجهاز أو البرنامج اللي ينتظر الطلبات، يعالجها، ويرجّع الجواب المناسب. مهم تلاحظ: السيرفر ما "يبدأ" الحديث أبداً — هو دايماً بموقع رد الفعل، ينتظر لين يوصله طلب.

البروتوكول: HTTP

HTTP (اختصار HyperText Transfer Protocol) هو "اللغة" أو مجموعة القواعد المتفق عليها اللي يحچي فيها العميل والسيرفر مع بعض. هو البروتوكول اللي يشغّل الويب كله تقريباً، وأغلب الـ Web APIs تستخدمه.

  • عديم الحالة (Stateless): كل طلب يوصل للسيرفر يعتبر مستقل تماماً عن الطلبات اللي قبله. السيرفر "ما يتذكر" مين أنت من طلب سابق — لازم كل طلب يحمل وياه كل المعلومات اللي يحتاجها السيرفر يفهمها ويعالجها (وهذا سبب رئيسي ليش نحتاج التوثيق بكل طلب، راح نشوفه بفصل لاحق).
  • قائم على الطلب/الرد: ما فيه اتصال مستمر مفتوح بشكل افتراضي — عميل يرسل طلب واحد، يستلم رد واحد، وخلصت الدورة (فيه استثناءات متقدمة زي WebSocket نذكرها بآخر الدورة).
  • يشتغل فوق TCP/IP: يعتمد بالأساس على بروتوكولات الشبكة الأساسية (TCP/IP) اللي توصّل البيانات من جهاز لجهاز عبر الإنترنت.
🔒
HTTP مقابل HTTPS: HTTPS هو نفس بروتوكول HTTP، بس مع طبقة تشفير إضافية اسمها TLS/SSL. هذا التشفير يمنع أي طرف ثالث (زي شخص على نفس شبكة الواي فاي) من قراءة أو التلاعب بالبيانات وهي بالطريق. أي API جدي ومحترف لازم يستخدم HTTPS فقط — بدون استثناء، حتى بمرحلة التطوير إذا أمكن.

دورة الطلب والرد خطوة بخطوة

  1. العميل يجهّز طلب HTTP: يحدد شنو يريد (Method + Endpoint)، ويرفقه بمعلومات إضافية (Headers) وأحياناً بيانات (Body).
  2. الطلب يسافر عبر الإنترنت لين يوصل للسيرفر الصحيح (عن طريق اسم النطاق زي api.example.com).
  3. السيرفر يستلم الطلب، يتحقق منه (هل المستخدم مصرّح له؟ هل البيانات صحيحة؟)، وينفّذ المطلوب (يقرأ من قاعدة بيانات، يحسب شي، يخزن معلومة...).
  4. السيرفر يرجّع رد HTTP: رمز حالة (Status Code) يوضح شنو صار، وربما بيانات (Body) وياه.
  5. العميل يستلم الرد ويتصرف على أساسه — يعرض البيانات، يظهر رسالة خطأ، أو يعيد المحاولة.

[ 02 ] العنونة

الـ Endpoint وتشريح الـ URL

Endpoint (نقطة النهاية) هو المصطلح اللي راح تسمعه أكثر شي وأنت تتعلم عن الـ APIs. بأبسط تعريف: الـ Endpoint هو عنوان (URL) محدد يمثّل مورد معيّن (Resource) أو عملية معينة، ويكون جاهز يستقبل طلبات بـ HTTP Method معيّن.

🎯
نقطة مهمة جداً: نفس الـ URL بالضبط، لو تغيّر الـ Method المستخدم وياه، يعتبر عملية مختلفة تماماً! GET /users/42 يعني "جيب لي بيانات المستخدم 42″، بينما DELETE /users/42 يعني "احذف المستخدم 42″. فعملياً، الـ Endpoint الحقيقي = Method + Path مع بعض، مو الـ Path لحاله.

تشريح الـ URL كامل

أي رابط (URL) تستخدمه بالـ API يتكوّن من عدة أجزاء، كل جزء له وظيفة مختلفة. خلي نفكك هذا المثال:

كل جزء من الـ URL له دور محدد — لاحظ إن الـ Fragment (بعد #) يبقى بالمتصفح ولا يوصل للسيرفر إطلاقاً
الجزءالمثالالوظيفة
Schemehttps://البروتوكول المستخدم للاتصال (http أو https)
Hostapi.example.comعنوان السيرفر (اسم النطاق) اللي راح يستقبل الطلب
Port:443المنفذ الشبكي؛ اختياري لأن 443 هو الافتراضي لـ HTTPS و80 لـ HTTP
Path/v1/users/42يحدد المورد المطلوب داخل السيرفر
Query String?active=true&sort=nameمعاملات إضافية اختيارية تعدّل الطلب (فلترة، ترتيب...)
Fragment#profileيُستخدم من المتصفح فقط للتنقل داخل الصفحة، غير مرسل للسيرفر

Path Parameters مقابل Query Parameters

هذا واحد من أكثر الأشياء اللي تلخبط المبتدئين، فخلينا نوضحها زين:

  • Path Parameter (معامل المسار): جزء أساسي من هوية المورد نفسه، يكون جزء من الـ Path مباشرة. مثال: بالـ Endpoint /users/{id}، الـ {id} هو Path Parameter — يحدد مين بالضبط المورد المطلوب. بدون قيمة له، الرابط ما يكتمل أصلاً.
  • Query Parameter (معامل الاستعلام): اختياري، يجي بعد علامة ?، ويُستخدم لتعديل أو فلترة أو ترتيب النتيجة. مثال: /users?active=true&limit=10 — يعني "جيب المستخدمين، بس بشرط يكونون فعّالين، وحدد لي أول 10 بس".
مقارنة عمليةPATH vs QUERY
// Path parameter — جزء من هوية المورد (إجباري)
GET /users/42

// Query parameters — تعديلات اختيارية على الطلب
GET /users?active=true&role=admin&page=2
📌
قاعدة عملية بسيطة: إذا القيمة تحدد "مين" المورد → استخدمها Path Parameter. إذا القيمة تعدّل أو تفلتر أو ترتّب قائمة نتائج → استخدمها Query Parameter.

HTTP Methods بالتفصيل الكامل

إذا الـ Path يحدد "وين" (أي مورد)، فالـ Method يحدد "شنو" تريد تسوي بيه. هذي هي "الأفعال" اللي يفهمها بروتوكول HTTP، وهي أساس مبدأ يسمى CRUD (إنشاء، قراءة، تعديل، حذف — Create, Read, Update, Delete).

GET

يجيب (يقرأ) بيانات من السيرفر بدون أي تغيير عليها. الأكثر استخدامًا من بين كل الـ Methods.

أكثر سؤال يتكرر — PUT مقابل PATCH: لو عندك مستخدم بثلاث حقول (اسم، إيميل، عمر) وتريد بس تغيّر العمر: مع PATCH ترسل {"age": 26} بس. مع PUT لازم ترسل الكائن كامل {"name":"...", "email":"...", "age": 26} — لأن PUT يعتبره "استبدال كامل"، وأي حقل ما ترسله ممكن ينمسح أو يرجع لقيمته الافتراضية!

مفهوم Safe و Idempotent

هذولا مصطلحين تقنيين يوصفون سلوك الـ Method، ومهم تفهمهم زين لأنهم يأثرون على تصميم أي API صح:

  • Safe (آمن): يعني الطلب لا يغيّر أي شي بحالة السيرفر — قراءة بس، بدون أي أثر جانبي.
  • Idempotent (مطابق النتيجة): يعني تكرار نفس الطلب عدة مرات متتالية يعطي نفس النتيجة النهائية بالضبط كأنك سويته مرة وحدة فقط. هذا مهم جدًا: لو انقطع الإنترنت وما تدري هل طلبك وصل أو لا، تقدر تعيد إرسال طلب Idempotent بأمان بدون خوف من نتائج غير متوقعة.

[ 04 ] الهيكل

بنية الطلب والرد الكاملة + رموز الحالة

شفنا بالمقدمة مثال مبسّط للطلب والرد. هسه خلينا نشوف البنية الرسمية الكاملة اللي يتبعها بروتوكول HTTP بالضبط، سطر بسطر.

بنية طلب HTTP (Request)

أي طلب HTTP يتكوّن من 4 أجزاء بالترتيب:

  1. سطر الطلب (Request Line): يحتوي الـ Method + الـ Path + نسخة البروتوكول.
  2. الـ Headers: سطر لكل Header، بصيغة Key: Value.
  3. سطر فارغ: يفصل بين الـ Headers والـ Body — تفصيلة صغيرة بس السيرفر يعتمد عليها ليعرف وين تخلص الـ Headers.
  4. الـ Body (اختياري): البيانات المرسلة، غالبًا بصيغة JSON.
خام (Raw) — RequestPOST
POST /v1/articles HTTP/1.1
Host: api.example.com
Content-Type: application/json
Authorization: Bearer eyJhbGciOi...
Content-Length: 58

{
  "title": "عنوان المقالة",
  "body": "محتوى المقالة هنا"
}

بنية رد HTTP (Response)

نفس المبدأ تقريبًا، بس السطر الأول يصير سطر الحالة (Status Line) بدل سطر الطلب:

خام (Raw) — Response201
HTTP/1.1 201 Created
Content-Type: application/json
Location: /v1/articles/501

{
  "id": 501,
  "title": "عنوان المقالة",
  "created_at": "2026-08-23T10:00:00Z"
}

رموز الحالة (HTTP Status Codes)

أول رقم برمز الحالة يحدد الفئة العامة للجواب. كمطوّر، لازم تحفظ الأكثر شيوعًا منها لأنها "لغة" السيرفر لإخبارك شنو صار بالضبط:

2xx — نجاح ✅

  • 200 OK — نجح الطلب، والرد يحتوي البيانات المطلوبة
  • 201 Created — تم إنشاء مورد جديد بنجاح (غالبًا بعد POST)
  • 204 No Content — نجح الطلب، بس ما فيه بيانات نرجعها (شائع مع DELETE)

3xx — إعادة توجيه ↪

  • 301 Moved Permanently — المورد انتقل لعنوان جديد بشكل دائم
  • 304 Not Modified — المورد ما تغيّر من آخر مرة، استخدم نسختك المخزّنة

4xx — خطأ من العميل ⚠

  • 400 Bad Request — صيغة الطلب فيها خطأ
  • 401 Unauthorized — التوثيق مفقود أو غير صحيح
  • 403 Forbidden — موثّق، لكن ما عندك صلاحية لهذا الإجراء
  • 404 Not Found — المورد المطلوب مو موجود
  • 409 Conflict — تعارض بحالة المورد (مثل بريد إلكتروني مسجّل مسبقًا)
  • 422 Unprocessable Entity — الصيغة صحيحة لكن البيانات غير منطقية
  • 429 Too Many Requests — تجاوزت الحد المسموح من الطلبات

5xx — خطأ من السيرفر ✕

  • 500 Internal Server Error — خطأ غير متوقع داخل السيرفر
  • 502 Bad Gateway — سيرفر وسيط استلم رد غير صالح من سيرفر آخر
  • 503 Service Unavailable — السيرفر مو جاهز مؤقتًا (صيانة أو ضغط زائد)
💡
قاعدة ذهبية: 4xx يعني "أنت (العميل) غلطت بشي بالطلب" — راجع طلبك. 5xx يعني "أنا (السيرفر) اللي عندي مشكلة" — المشكلة مو بيدك كمستخدم للـ API.

[ 05 ] البيانات

صيغة البيانات: JSON

لازم يكون الـ Body مكتوب بصيغة يفهمها الطرفين (العميل والسيرفر) بنفس الطريقة بالضبط. أكثر صيغة منتشرة اليوم بعالم الـ APIs هي JSON (اختصار JavaScript Object Notation) — صيغة نصية خفيفة، سهلة القراءة للبشر، وسهلة المعالجة للبرامج.

مثال JSON كامل.json
{
  "id": 42,
  "name": "أحمد علي",
  "isActive": true,
  "age": 26,
  "email": null,
  "roles": ["admin", "editor"],
  "address": {
    "city": "بغداد",
    "country": "العراق"
  }
}

القواعد الأساسية بسيطة:

  • البيانات مبنية على أزواج مفتاح-قيمة ("key": value)، محاطة بأقواس معقوفة { } لتكوين "كائن" (Object).
  • المفاتيح (Keys) دايمًا نصوص (Strings) محاطة بعلامات اقتباس مزدوجة.
  • القيم (Values) ممكن تكون: نص "..."، رقم 26، قيمة منطقية true/false، فارغة null، مصفوفة [...]، أو كائن متداخل {...} آخر.
  • المصفوفات (Arrays) تُكتب بأقواس مربعة [ ] وتقدر تحتوي عدة عناصر مفصولة بفواصل.
ℹ️
وشنو عن XML؟ قبل انتشار JSON، كانت صيغة XML هي الأكثر شيوعًا (ولسه مستخدمة بأنظمة قديمة أو مؤسسية زي SOAP). XML أطول وأكثر تعقيدًا بالكتابة (تحتاج وسوم فتح وغلق لكل عنصر)، لهذا JSON أصبح الخيار الافتراضي بأغلب الـ APIs الحديثة لخفّته وسهولته.

REST API ومبادئه

REST (اختصار Representational State Transfer) مو بروتوكول ولا معيار رسمي صارم — هو أسلوب معماري (مجموعة مبادئ وأفكار) لتصميم APIs، اقترحه Roy Fielding سنة 2000. أي API يتبع هذي المبادئ نسميه "RESTful"، وهو الأسلوب الأكثر انتشارًا اليوم.

المبادئ الستة لـ REST

  • فصل العميل عن السيرفر (Client-Server): الاثنين مستقلين عن بعض، يتفقون بس على شكل الـ API. تقدر تغيّر تصميم الواجهة الأمامية بدون ما تلمس السيرفر، والعكس صحيح.
  • عديم الحالة (Stateless): كل طلب لازم يحمل كل المعلومات اللي يحتاجها السيرفر — بدون ما يعتمد على "ذاكرة" من طلبات سابقة.
  • قابلية التخزين المؤقت (Cacheable): الردود لازم توضّح هل تصلح للتخزين المؤقت أو لا، عشان تحسين الأداء وتقليل الضغط على السيرفر.
  • واجهة موحّدة (Uniform Interface): نفس الأنماط والقواعد تنطبق على كل الموارد — نفس طريقة التسمية، نفس استخدام الـ Methods، بدون استثناءات عشوائية.
  • نظام متعدد الطبقات (Layered System): العميل ما يحتاج يعرف هل هو متصل بالسيرفر مباشرة أو عبر وسطاء (Load Balancer، API Gateway...).
  • كود عند الطلب (Code on Demand): مبدأ اختياري نادر الاستخدام — يسمح للسيرفر يرسل كود قابل للتنفيذ للعميل (أقرب لصفحات الويب من الـ APIs العادية).

كيف تسمّي الموارد (Resource Naming)

بأسلوب REST، كل شي يتعامل معه كـ مورد (Resource) — مستخدمين، مقالات، طلبات شراء... وتسمية الروابط تتبع اتفاقيات معينة:

القاعدة✓ صحيح✗ خطأ
استخدم أسماء (Nouns) مو أفعال/articles/getArticles
صيغة الجمع للمجموعات/users/user
حروف صغيرة وشرطات/order-items/orderItems
الموارد المتداخلة بعلاقة واضحة/users/42/orders/getOrdersByUser?id=42
📌
الفعل (Method) هو اللي يحدد العملية — الاسم بالرابط يبقى ثابت دايمًا. نفس المورد /articles/9 يُستخدم مع GET للقراءة، PUT/PATCH للتعديل، وDELETE للحذف — بدون ما تحتاج روابط منفصلة لكل عملية.

Authentication و Authorization

هذولا مصطلحين يتلخبطون على أغلب المبتدئين رغم إنهم مختلفين تمامًا:

🪪
Authentication (المصادقة/التوثيق) = "مين إنت؟" — إثبات هويتك (تسجيل الدخول).
Authorization (التفويض/الصلاحيات) = "شنو مسموح لك تسوي؟" — بعد ما تثبت هويتك، شنو الصلاحيات المتاحة لك.

بكلمة وحدة: تثبت هويتك أول (Authentication)، وبعدين النظام يقرر شنو مسموح لك (Authorization). خلي نستعرض الطرق الشائعة لتطبيق هذا:

1) مفاتيح API (API Keys)

أبسط طريقة — السيرفر يعطيك نص طويل عشوائي (مفتاح) لما تسجّل تطبيقك، وترسله مع كل طلب (غالبًا بـ Header أو Query Parameter). يفيد أكثر بتحديد مين التطبيق اللي يستخدم الـ API (لأغراض التتبع وتحديد حدود الاستخدام)، أكثر من تحديد هوية مستخدم فردي.

مثالHeader
X-API-Key: sk_live_51Hh2x9KJp3mN8qR...

2) Basic Authentication

ترسل اسم المستخدم وكلمة المرور مع كل طلب، مشفّرة بصيغة Base64 (تنويه: Base64 تشفير عكسي بسيط، مو تشفير حقيقي — أي شخص يقدر يفك تشفيرها بثانية). لهذا السبب استخدامها آمن فقط فوق HTTPS.

مثالHeader
Authorization: Basic YWhtZWQ6bXlwYXNzd29yZDEyMw==

3) OAuth 2.0

OAuth 2.0 إطار عمل (Framework) يسمح لتطبيق يوصل لبيانات محمية بالنيابة عن المستخدم، بدون ما المستخدم يشارك كلمة سره مع هذا التطبيق إطلاقًا. هذا اللي يصير لما تضغط "تسجيل الدخول بحساب Google" بأي موقع — الموقع ما يشوف كلمة سر Google متاعتك أبدًا.

تدفّق Authorization Code — أكثر أنواع تدفقات OAuth 2.0 أمانًا وشيوعًا
⚠️
لأمان إضافي (خصوصًا بتطبيقات الموبايل والـ SPA)، يُستخدم امتداد اسمه PKCE يمنع سرقة رمز التفويض أثناء الخطوة 3-4. تجنّب استخدام أنواع OAuth القديمة زي Implicit Grant أو Password Grant — أصبحت غير مستحسنة أمنيًا اليوم.

4) JWT — JSON Web Token

JWT صيغة توكن مضغوطة، غالبًا تُستخدم كشكل لـ Access Token بأنظمة OAuth أو بشكل مستقل. يتكوّن من 3 أجزاء مفصولة بنقطة، كل جزء مُرمّز بصيغة Base64Url:

Header.Payload.Signature — الأجزاء الثلاثة مفصولة بنقاط، هذا هو شكل JWT الحقيقي
🚨
تحذير مهم جدًا: الـ Payload مُرمّز بـ Base64Url فقط — مو مشفّر! أي شخص يقدر يفك ترميزه ويقرأ محتواه بسهولة (جرّب موقع jwt.io). لا تحط أبدًا معلومات حساسة (كلمات مرور، أرقام بطاقات) داخل الـ Payload. الشي المحمي فعليًا هو التوقيع بس — يمنع أي احد يعدّل المحتوى بدون ما يكتشف السيرفر التلاعب.

[ 08 ] الحماية

أمان الـ API (API Security)

الأمان الحقيقي مو "خطوة وحدة تسويها وتخلص" — هو طبقات متتالية من الحماية، كل طبقة تصيد نوع مختلف من المشاكل. لو طبقة وحدة انخرقت، الطبقات الثانية لسه تحميك (مبدأ يسمى Defense in Depth).

كل طلب يمر عبر هالطبقات بالترتيب — أي طبقة توقفه لو فيها مشكلة، قبل لا يوصل للبيانات الحساسة

Rate Limiting — تحديد معدّل الطلبات

بدون حد أقصى، أي شخص (أو بوت) يقدر يرسل آلاف الطلبات بالثانية — يعطّل السيرفر، أو يحاول يخمّن كلمات مرور بالتجربة والخطأ. الحل: السيرفر يحسب عدد طلبات كل مستخدم/IP خلال فترة زمنية معينة، ولو تجاوز الحد يرجّع 429 Too Many Requests. غالبًا يخبرك السيرفر بحالتك عن طريق Headers مخصصة:

مثالResponse Headers
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 23
X-RateLimit-Reset: 1699004000

التحقق من المدخلات (Input Validation)

قاعدة ذهبية: لا تثق أبدًا بأي بيانات جاية من العميل، حتى لو تطبيقك أنت اللي أرسلها! لازم تتحقق من نوع وطول وصيغة كل قيمة على السيرفر (مو بس بجافاسكربت بالمتصفح، لأن أي شخص يقدر يتجاوز التحقق من جهة العميل بسهولة). هذا يحميك من هجمات زي SQL Injection، ومن بيانات فاسدة تخرب قاعدة بياناتك.

CORS — مين يقدر يستدعي API من متصفح؟

المتصفحات تطبّق قاعدة أمان اسمها Same-Origin Policy: كود JavaScript بموقع "أ" ما يقدر افتراضيًا يستدعي API بموقع "ب" مختلف. CORS هو آلية تسمح للسيرفر يحدد بصراحة "مين مسموحله يستدعيني من متصفح" عن طريق Header اسمه Access-Control-Allow-Origin. تذكر Method الـ OPTIONS من الفصل الثالث؟ هذا بالضبط استخدامه الرئيسي — المتصفح يرسله تلقائيًا كـ"طلب استطلاعي" (Preflight) قبل الطلب الحقيقي بحالات معينة.

ℹ️
CORS حماية خاصة بالمتصفح فقط — ما تحمي من طلبات تجي مباشرة من سيرفر لسيرفر، أو من أدوات زي Postman أو curl. هي طبقة إضافية، مو بديل عن Authentication و Authorization.

API Gateway

بالأنظمة الكبيرة اللي فيها عدة خدمات خلفية منفصلة (Microservices)، ما تريد تكرر منطق التوثيق وRate Limiting بكل خدمة لحالها. API Gateway يشتغل كنقطة دخول موحّدة: يستقبل كل الطلبات، يطبّق التوثيق والـ Rate Limiting مركزيًا، وبعدين يوجّه كل طلب للخدمة الداخلية المناسبة.

قائمة تحقق سريعة لأمان API

✅
استخدم HTTPS فقط بدون استثناء — حتى بالتطوير لو أمكن
لا تخزّن كلمات المرور كنص صريح — استخدم دوال Hashing متخصصة مثل bcrypt
لا تكشف تفاصيل تقنية حساسة برسائل الخطأ (Stack Traces) للمستخدم النهائي
تحقق من الصلاحيات (Authorization) على كل Endpoint، مو بس عند تسجيل الدخول
لا تحط مفاتيح API أو أسرار داخل الكود مباشرة — استخدم متغيرات بيئة (Environment Variables)
حدّث المكتبات والاعتماديات باستمرار لسد الثغرات المعروفة
سجّل (Log) الأنشطة المشبوهة وراقبها بانتظام

تصميم API احترافي من الصفر

لحد هسه تعلمنا "قطع الغيار" — هسه خلينا نشوف القرارات اللي تفرّق بين API عشوائي وAPI مصمّم باحترافية.

Versioning — التحكم بالإصدارات

مع مرور الوقت، راح تحتاج تغيّر شكل الـ API — وبعض التغييرات "كاسرة" (Breaking Changes) تخرّب أي تطبيق يستخدم النسخة القديمة. الحل: كل نسخة جديدة تاخذ رقم، والنسخة القديمة تبقى شغالة لفترة انتقالية.

الطريقةمثالملاحظة
ترقيم بالرابط (URI)/v1/usersالأشهر والأبسط — واضح ومرئي مباشرة
ترقيم بالـ HeaderAccept: ...v2+jsonروابط أنظف، بس أقل وضوحًا للمطوّرين الجدد
ترقيم بمعامل استعلام?version=2نادر الاستخدام
📌
كمبتدئ، اعتمد ترقيم الرابط (/v1/...) — أبسط طريقة تفهمها وتطبقها بدون تعقيد إضافي.

Pagination — تقسيم النتائج الكبيرة

لو عندك مليون سجل بقاعدة البيانات، ما تقدر ترجعهم كلهم برد وحد! لازم تقسمهم لصفحات:

  • Offset/Limit: ?limit=20&offset=40 — "جيب لي 20 نتيجة، ابدأ من رقم 40". بسيط، بس ممكن يصير فيه تكرار أو تخطي نتائج لو البيانات تغيّرت بين الطلبات.
  • Cursor-based: ?cursor=eyJpZCI6NDB9&limit=20 — يستخدم "مؤشر" يشاور لآخر نقطة توقفت عندها، أكثر موثوقية مع البيانات الكبيرة أو سريعة التغيّر (تستخدمه Stripe وTwitter مثلاً).
رد يحتوي معلومات الصفحاتJSON
{
  "data": [ ... ],
  "pagination": {
    "total": 530,
    "limit": 20,
    "offset": 40,
    "next": "/v1/users?limit=20&offset=60"
  }
}

الفلترة والترتيب والبحث

اتفاقية شائعة عبر معاملات الاستعلام: ?status=active&sort=-created_at&search=ahmed — لاحظ إشارة الناقص (-) قبل created_at: اتفاقية شائعة تعني "ترتيب تنازلي"، بينما بدون إشارة يعني تصاعدي.

معالجة الأخطاء بشكل موحّد

لما يصير خطأ، لازم شكل رسالة الخطأ يكون ثابت وموحّد عبر كل الـ Endpoints — عشان كود العميل يقدر يتعامل معه بشكل متوقّع، بدل ما يفاجئ بشكل مختلف بكل مرة:

شكل خطأ موحّد422
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "البريد الإلكتروني غير صالح",
    "details": [
      { "field": "email", "issue": "invalid_format" }
    ]
  }
}

التوثيق — OpenAPI و Swagger

API بدون توثيق تقريبًا عديم الفائدة لأي مطوّر ثاني. معيار OpenAPI (يُعرف سابقًا بـ Swagger) هو صيغة موحّدة (YAML أو JSON) تصف كل Endpoint: شنو Methods المتاحة، شنو المعاملات المطلوبة، شكل الرد المتوقع، وطريقة التوثيق. أدوات زي Swagger UI تاخذ هذا الملف وتحوّله لصفحة تفاعلية يقدر أي مطوّر يجرّب فيها الـ Endpoints مباشرة من المتصفح.

HATEOAS (نظرة سريعة)

مبدأ متقدم من REST يخلي الرد "يشرح نفسه" — يحتوي روابط للعمليات المتاحة تاليًا. مثلاً رد عن طلبية معينة ممكن يحتوي رابط "إلغاء" فقط لو الطلبية لسه قابلة للإلغاء. مفيد نظريًا، بس نادرًا ما يُطبّق بشكل كامل بالمشاريع الواقعية — يكفي تعرف المفهوم.

مفتاح عدم التكرار (Idempotency Key)

لعمليات POST الحساسة (زي الدفع الإلكتروني)، العميل يرسل Header فريد اسمه Idempotency-Key مع الطلب. لو انقطع الاتصال والعميل أعاد إرسال نفس الطلب بنفس المفتاح، السيرفر يتعرف عليه ويرجّع نفس النتيجة الأولى بدل ما ينفّذ العملية (الدفع) مرتين.

أدوات عملية لأي مطوّر

Postman

برنامج رسومي منتشر جدًا لبناء وإرسال واختبار طلبات API بدون ما تكتب أي كود. تختار الـ Method، تكتب الرابط، تضيف Headers والـ Body، تضغط Send، وتشوف الرد كامل — رمز الحالة، الوقت المستغرق، والبيانات بشكل منسّق وملوّن. يفيد كثير لاستكشاف API قبل ما تربطه فعليًا بتطبيقك، ويسمح لك تحفظ مجموعات طلبات (Collections) ومتغيرات بيئة (زي رابط مختلف للتطوير والإنتاج).

curl

أداة سطر أوامر موجودة بأغلب الأنظمة افتراضيًا، ممتازة للاختبار السريع أو التوثيق أو الأتمتة بالسكربتات:

مثال GETcurl
curl -X GET https://api.example.com/v1/users/42 \
  -H "Authorization: Bearer eyJhbGciOi..."
مثال POSTcurl
curl -X POST https://api.example.com/v1/articles \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer eyJhbGciOi..." \
  -d '{"title": "عنوان", "body": "محتوى"}'

أدوات ثانية تستحق المعرفة

  • Insomnia: بديل لـ Postman، بواجهة أخف وأبسط.
  • Network tab بأدوات المطوّر بالمتصفح: يخليك تشوف كل الطلبات اللي يرسلها موقع أو تطبيق ويب فعليًا، مفيد جدًا للتصحيح.
  • Swagger UI: إذا الـ API موثّق بـ OpenAPI، تقدر تجرّب كل Endpoint مباشرة من صفحة التوثيق نفسها.

GraphQL و SOAP و WebSocket — نظرة سريعة

REST هو الأكثر انتشارًا، بس مو الوحيد. مهم تعرف الأنماط الثانية عشان تميّزها لو صادفتها:

النمطنقاط الدخولالصيغةالاستخدام الأمثل
RESTعدة Endpoints (مورد لكل رابط)JSON غالبًاالأغلبية الساحقة من الـ APIs الحديثة
GraphQLEndpoint واحد فقطJSONلما تريد تتحكم بالضبط بالحقول اللي ترجع، وتتجنب طلبات زايدة
SOAPعادة نقطة واحدة بعمليات محددةXML فقطأنظمة مؤسسية قديمة (بنوك، تأمين) بمعايير صارمة
WebSocketاتصال واحد مستمر مفتوحأي صيغةتحديثات لحظية — شات مباشر، أسعار أسهم، إشعارات فورية

GraphQL يحل مشكلة شائعة بـ REST: تخيل صفحة تحتاج بس اسم المستخدم وصورته، بس الـ Endpoint يرجّعلك كل بياناته (اسم، إيميل، عنوان، تاريخ الميلاد...) — هذا يسمى Over-fetching. مع GraphQL، العميل يكتب "استعلام" يحدد بالضبط الحقول اللي يريدها بس، ويرجعله السيرفر نفس الشكل المطلوب بالضبط، لا أكثر ولا أقل.

WebSocket مختلف بجوهره عن REST — بدل دورة طلب/رد منفصلة لكل عملية، يفتح قناة اتصال وحدة تبقى مفتوحة، ويقدر الطرفين (العميل والسيرفر) يرسلون رسائل بأي اتجاه بأي وقت. هذا أساس تطبيقات الشات المباشر والإشعارات اللحظية.

الخلاصة، مسرد المصطلحات، وخطواتك الجاية

إذا وصلت هنا، صار عندك فهم شامل لكل الأساسيات اللي يحتاجها أي مطوّر API — من التعريف الأساسي، مرورًا بـ HTTP والـ Methods، للأمان والتصميم الاحترافي. الخطوة الجاية هي التطبيق العملي:

  1. جرّب API عام مجاني بـ Postman — مثل jsonplaceholder.typicode.com للتجربة بدون تسجيل، أو أي API طقس مجاني.
  2. اقرأ توثيق API حقيقي كامل (زي GitHub API أو Stripe) وشوف كيف طبّقوا المبادئ اللي تعلمتها بهذي الدورة عمليًا.
  3. ابني مشروع بسيط شخصي — نفس فكرة Todo API اللي شفناها، بس نفّذها فعليًا بأي لغة تعرفها.
  4. تمرّن على قراءة وكتابة JSON بسرعة وبدون أخطاء بالصياغة.
  5. جرّب تطبّق تسجيل دخول حقيقي بـ OAuth (زي "تسجيل الدخول بـ Google") بمشروع صغير.

مسرد المصطلحات

API
واجهة برمجة التطبيقات — مجموعة قواعد تسمح لبرنامجين يتواصلون مع بعض.
Endpoint
عنوان (URL) محدد مع طريقة (Method) معينة، يمثّل عملية واحدة على مورد.
Client / Server
العميل يبدأ الطلب، والسيرفر يستقبله ويرد عليه.
HTTP / HTTPS
البروتوكول الأساسي لأغلب Web APIs؛ HTTPS نسخة مشفّرة منه.
Request / Response
الطلب اللي يرسله العميل، والرد اللي يرجّعه السيرفر.
Header
معلومة إضافية توصف الطلب أو الرد (نوع المحتوى، التوثيق...).
Body
البيانات الفعلية المرسلة أو المستلمة داخل الطلب أو الرد.
Status Code
رقم من 3 خانات يوضح نتيجة الطلب (200، 404، 500...).
JSON
صيغة نصية خفيفة لتمثيل البيانات المنظمة، الأكثر استخدامًا اليوم.
REST
أسلوب معماري لتصميم APIs يعتمد على الموارد وHTTP Methods.
Authentication
إثبات هوية المستخدم — "مين إنت؟"
Authorization
تحديد صلاحيات المستخدم بعد إثبات هويته — "شنو مسموح لك؟"
Token
نص موقّع يثبت هوية المستخدم بدل إرسال كلمة السر بكل طلب.
JWT
صيغة توكن قياسية بثلاث أجزاء: Header، Payload، Signature.
OAuth
إطار عمل يسمح بتفويض الوصول لتطبيق بدون مشاركة كلمة السر.
Rate Limiting
تحديد عدد الطلبات المسموحة لكل مستخدم خلال فترة زمنية.
CORS
آلية تتحكم بمين يقدر يستدعي API من متصفح على نطاق مختلف.
Idempotent
خاصية: تكرار نفس الطلب عدة مرات يعطي نفس النتيجة النهائية.
Pagination
تقسيم نتائج كبيرة لصفحات أصغر بدل إرجاعها كلها دفعة وحدة.
Webhook
آلية عكسية: السيرفر "يستدعيك" هو لما يصير حدث معين، بدل ما تسأل انت باستمرار.
🚀
أفضل طريقة تثبّت فيها هذا الكلام كله: افتح Postman هسه، جرّب أي API عام، وشوف بعينك الطلب والرد وهم يصيرون حقيقة — مو بس كلام تقرأه.
